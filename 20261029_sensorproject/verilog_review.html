공유 tick의 enable은 MUX 말고 OR로

SR04와 DHT11이 1 µs tick 생성기 tick_gen_us_sr04 하나를 같이 씁니다. tick_gen은 enable = 1일 때만 tick을 만듭니다.

배운 점

  1. 한 wire에 두 모듈의 출력을 직접 연결하면 multi-driven net 오류가 납니다. 출력은 각자 다른 wire(w_enable_sr04, w_enable_dht11)로 받고 나서 합칩니다.
  2. MUX(w_mode4 ? a : b)로 합치면 화면에 보이는 센서만 tick을 받습니다. 측정 도중 mode를 바꾸면 tick이 끊겨서 센서 FSM이 그 상태에 갇힙니다.
  3. OR로 합치면 일하고 있는 센서는 누구든 tick을 받습니다. mode를 바꿔도 측정이 끝까지 진행됩니다.
  4. assign에는 어떤 조합 논리식이든 넣을 수 있습니다. 공유 자원을 요청하는 신호를 OR로 묶는 건 흔한 패턴입니다.
오류한 wire에 출력 두 개 연결
주의MUX: mode 전환 시 tick 끊김
정답OR: 요청한 쪽은 누구든 tick

예시 코드

// (X) multi-driven: 한 wire에 출력 두 개
controll_unit_sr04 U_SR04 (.enable(w_enable), ...);
dht11_controller   U_DHT  (.enable(w_enable), ...);

// (주의) MUX: mode 바꾸면 진행 중인 센서 tick 끊김
wire w_enable_sr04, w_enable_dht11;
assign w_enable = (w_mode4) ? w_enable_dht11 : w_enable_sr04;

// (O) OR: 일하는 센서는 누구든 tick 받음
assign w_enable = w_enable_dht11 | w_enable_sr04;
tick_gen_us_sr04 U_TICK (.clk(clk), .rst(rst), .enable(w_enable), .b_tick(w_b_tick));

// assign 응용
assign w_busy  = w_enable_dht11 & w_enable_sr04;     // 둘 다 동작 중
assign w_start = (w_R & w_mode3) | (w_R & w_mode4);  // 조건 묶기

FND에 글자 니블(d, H, t) 표시하기

거리 123을 FND에 d123으로 띄우려고 {4'b1101, 백의자리}를 fnd_controller로 보냈습니다. 그런데 fnd_controller 안의 digit_splitter가 % 10, / 10으로 다시 10진 분해를 해서, 0xD1 = 209가 화면에 09로 나왔습니다.

배운 점

  1. 값을 어떻게 만드느냐(208 + d든 {4'hD, d}든)는 상관없습니다. 받는 쪽이 10진 분해를 하는 게 문제입니다. 글자 니블을 넣는 모드에서는 분해를 건너뛰고 상위·하위 니블을 그대로 써야 합니다.
  2. {} 연결 안에서 각 항은 자기 크기로 계산됩니다. (dsin/100)%10은 상수 100, 10이 32비트라서 결과도 32비트입니다. 연결한 뒤 8비트로 잘리면 앞에 붙인 4'hD가 사라집니다. 4비트 wire로 먼저 만든 다음 붙이세요.
  3. {176, x}처럼 크기 없는 상수는 {} 안에 쓸 수 없습니다. {4'hB, x}처럼 비트 폭을 붙이세요.

예시 코드

// fnd_mux 쪽: 니블 단위로 포장
wire [3:0] hund = (dsin / 100) % 10;   // 먼저 4비트로 확정
assign ds_sec  = {4'b1101, hund};      // 'd' + 백의자리  (O)
// assign ds_sec = {4'b1101, (dsin/100)%10};  // 32비트 → 'd' 잘림 (X)
// assign ds_sec = {176, hund};               // 크기 없는 상수 (X)

// fnd_controller 쪽: 센서 모드면 10진 분해 우회
wire raw = (mode == 4'b0010) | (mode == 4'b0001);
assign w_sec_ds1  = raw ? sec[3:0] : sec % 10;
assign w_sec_ds10 = raw ? sec[7:4] : (sec / 10) % 10;

오픈드레인 inout 핀에는 PULLUP

DHT11은 선 하나(dht11_io)로 FPGA와 센서가 번갈아 말하는 오픈드레인 버스입니다. FPGA는 자기 차례가 끝나면 1'bz로 선을 놓고, 센서는 선을 LOW로 끌어내리기만 합니다.

배운 점

  1. 아무도 선을 구동하지 않으면(Z) 값이 떠 있어서 FPGA가 0과 1을 랜덤하게 읽습니다. 그러면 SYNCL 응답 검출부터 실패합니다.
  2. 풀업 저항이 "아무도 안 잡으면 1"을 만들어 줍니다. FPGA 핀의 내부 풀업은 XDC의 PULLUP true로 켤 수 있습니다.
  3. 센서 모듈 보드에 풀업 저항이 달려 있으면 없어도 동작하지만, 켜 두는 게 안전합니다.
  4. 시뮬레이션에는 XDC가 적용되지 않습니다. 테스트벤치에 pullup(dht11_io);를 따로 넣어야 합니다.

예시 코드

RTL: 내 차례가 아니면 선 놓기

assign dht11_io = (dht11_io_control_reg) ? dht11_io_reg : 1'bz;

XDC

# 방법 1: dict 안에 같이 쓰기
set_property -dict { PACKAGE_PIN B16 IOSTANDARD LVCMOS33 PULLUP true } [get_ports {dht11_io}]
# 방법 2: 따로 한 줄
set_property PULLUP true [get_ports dht11_io]

테스트벤치: 시뮬레이션용 풀업

wire dht11_io;
pullup (dht11_io);
assign dht11_io = sensor_oe ? sensor_o : 1'bz;

같은 원리가 적용되는 곳: I2C의 SDA·SCL, 1-wire 센서

tx_sender에서 쓴 기법들

0.5초마다 FND의 8자리(4비트씩)를 UART로 1234 5678\r\n처럼 보내는 모듈입니다. 처음 보는 문법과 설계 방법이 여러 개 들어 있습니다.

function: 같은 조합 로직을 여러 번 재사용

모듈 안에서 입력→출력 계산을 함수로 묶어 여러 곳에서 호출합니다. 합성하면 호출한 곳마다 조합회로가 복사됩니다. 서브모듈을 줄줄이 인스턴스하는 것보다 짧습니다.

function [7:0] to_ascii(input [3:0] digit);   // 반환 폭 [7:0]
    case (digit)
        4'hB:    to_ascii = "H";               // 함수 이름에 대입 = 반환값
        4'hC:    to_ascii = "t";
        4'hD:    to_ascii = "d";
        default: to_ascii = 8'h30 + digit;     // '0'~'9'
    endcase
endfunction

tx_data = to_ascii(snap_reg[31:28]);
  • 함수 안에서는 #지연, @, <=를 쓸 수 없습니다. 순수 조합 계산만 됩니다.
  • task와 차이: task는 시간 지연이 가능해서 테스트벤치용이고, function은 값을 즉시 반환하며 합성할 수 있습니다.

문자열 리터럴 "A" = 8비트 ASCII 값

"H"는 8'h48과 같습니다. 한 글자가 8비트라서 ASCII 표를 외울 필요가 없습니다.

tx_data = " ";      // 8'h20
tx_data = "d";      // 8'h64
tx_data = 8'h0D;    // '\r' (Carriage Return): 줄 맨 앞으로
tx_data = 8'h0A;    // '\n' (Line Feed): 다음 줄로

숫자 0~9를 ASCII로 바꿀 때는 8'h30 + digit입니다('0' = 0x30). 터미널에서 줄을 바꾸려면 보통 \r\n을 둘 다 보냅니다.

Snapshot: 보내는 동안 값이 바뀌는 문제 막기

11바이트 × 10비트 ÷ 9600 bps ≈ 11.5 ms가 걸립니다. 그 사이 msec(10 ms마다 바뀜)가 바뀌면 한 줄 안에 서로 다른 시점의 값이 섞입니다. 그래서 전송을 시작하는 순간 8자리를 32비트 레지스터에 한 번에 저장하고, 전송 중에는 저장한 값만 씁니다.

IDLE: if (period_tick) begin
    snap_next = {w_hour_ds10, w_hour_ds1, w_min_ds10, w_min_ds1,
                 w_sec_ds10,  w_sec_ds1,  w_msec_ds10, w_msec_ds1};
    n_state = SEND;
end

{} 연결로 4비트 8개를 32비트 하나로 묶고, 꺼낼 때는 snap_reg[31:28]처럼 잘라 씁니다.

busy 핸드셰이크 FSM (IDLE → SEND → WAIT)

uart_tx는 한 번에 1바이트만 보낼 수 있습니다. "보내도 돼?(busy=0)" → start 1클럭 → busy가 0이 될 때까지 대기, 이 과정을 반복합니다.

SEND: if (!tx_busy) begin tx_start = 1'b1; n_state = WAIT; end   // 1클럭 펄스
WAIT: if (!tx_busy) begin
          if (byte_cnt == LAST_BYTE) n_state = IDLE;
          else begin byte_cnt_next = byte_cnt + 1; n_state = SEND; end
      end
  • WAIT가 필요한 이유: SEND에서 바로 다음 바이트로 넘어가면 busy가 아직 0인 클럭에 start를 또 줘서 바이트가 겹칩니다.
  • 이게 맞물리려면 uart_tx의 busy가 start 다음 클럭에 바로 1, STOP이 끝나는 클럭에 바로 0이 되어야 합니다. 그래서 uart_datastate.v의 IDLE if(tx_start) 안과 STOP 끝에서 tx_busy_next를 바꿨습니다.
  • 보낼 바이트는 byte_cnt로 case문 MUX를 만들어 tx_data에 고릅니다. uart_tx가 start 클럭에 tx_data를 래치하므로 그 클럭에만 맞으면 됩니다.

FIFO가 필요 없는 경우

FIFO는 데이터가 언제 올지 모르고 받는 쪽이 느릴 때 쌓아 두는 버퍼입니다(예: UART RX → 디코더). sender는 8자리가 이미 동시에 다 있고 보낼 순서도 정해져 있어서, 카운터로 하나씩 고르면 끝입니다. 게다가 기존 FIFO는 DEPTH=4라 11바이트를 담지 못합니다.

주기 만들기: tick 모듈 대신 카운터 하나

if (period_cnt == PERIOD - 1) begin period_cnt <= 0; period_tick <= 1; end
else period_cnt <= period_cnt + 1;

0.5 s = 100 MHz × 0.5 = 50,000,000 클럭입니다. 1 µs tick × 500,000처럼 두 단계로 나눌 필요가 없습니다. 카운터 폭은 $clog2(PERIOD) = 26비트입니다.

parameter 오버라이드로 시뮬레이션 빠르게

#(parameter PERIOD = 50_000_000)로 선언해 두고, 테스트벤치에서만 작은 값으로 바꿔 끼웁니다. 실제 0.5초를 시뮬레이션하면 너무 오래 걸립니다.

tx_sender #(.PERIOD(20000)) DUT (...);   // TB에서만 20000클럭 주기

baud tick도 테스트벤치에서 4클럭마다 1이 되도록 빠르게 만들어 썼습니다.

테스트벤치 검증: 내가 만든 uart_rx를 수신기로 재사용

tx 파형을 눈으로 읽는 대신, 프로젝트의 uart_rx를 테스트벤치에 붙여 tx를 다시 받아서 글자로 출력하면 자동으로 확인됩니다.

uart_rx U_RX (.clk(clk), .rst(rst), .rx(tx), .b_tick(baud_tick),
              .rx_data(rx_data), .rx_done(rx_done));
always @(posedge clk) if (rx_done) $write("%c", rx_data);   // %c = 문자로 출력

결과는 1234 5678\r\n, d123 d123\r\n, t025 H045\r\n로 총 33바이트였습니다. 전송 도중 입력값을 바꿔도 첫 줄이 1234 5678로 유지되어 snapshot이 동작하는 것도 확인했습니다.
