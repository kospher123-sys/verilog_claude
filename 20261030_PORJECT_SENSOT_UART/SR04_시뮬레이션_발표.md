## 1. 모듈 구조와 FSM (0:00 ~ 0:50)

**슬라이드 내용**
- `sr04_top` = `SR04_sensor`(FSM) + `baud_tick_gen_sr04`(1us tick, 100클럭마다)
- FSM: `IDLE → START → WAIT → DISTANCE → STOP → IDLE`

| 상태 | 하는 일 | 빠져나가는 조건 |
|---|---|---|
| IDLE | tick 카운터 clear, start 대기 | start 수락 |
| START | trigger = 1 | 1us tick 12개 (약 12us) |
| WAIT | echo 상승 대기 | echo = 1 → DISTANCE / 36ms → 타임아웃 |
| DISTANCE | 58us마다 1cm 증가 | echo = 0 → 거리 저장 / 36ms → 타임아웃 |
| STOP | 약 10ms 휴식 | → IDLE |

- 안정성 장치 3가지: echo 2-FF 동기화기, 60ms 최소 측정 주기, 36ms 타임아웃

**대본**
> sr04_top은 초음파 센서 HC-SR04를 제어하는 모듈입니다. 안에는 상태 머신 하나와, 100MHz 클럭을 나눠서 1마이크로초마다 tick을 만드는 분주기가 있습니다.
> 동작 순서는 다섯 상태입니다. start가 들어오면 START 상태에서 trigger를 약 12마이크로초 동안 올리고, WAIT에서 echo가 올라오길 기다립니다. echo가 올라오면 DISTANCE 상태에서 58마이크로초마다 1센티미터씩 셉니다. 소리가 왕복하니까 1센티미터에 58마이크로초가 걸리기 때문입니다. echo가 내려가면 그 값을 거리로 저장하고, STOP에서 10밀리초 쉰 다음 IDLE로 돌아갑니다.
> 그리고 실제 보드에서 문제가 생기지 않도록 세 가지 보호 장치를 넣었습니다. echo 입력 동기화, 60밀리초 최소 측정 주기, 그리고 36밀리초 타임아웃입니다.

## 2. 테스트 전략 (0:50 ~ 1:20)

**슬라이드 내용**
- 센서 모델 task `sensor_echo(echo_us)`: trigger 하강 → 200us 후 echo를 `거리 × 58us` 동안 high
- start는 버튼/UART 명령과 같은 **1클럭 펄스**로 입력
- `check()` task로 기대값 비교 → `[PASS]/[FAIL]` 자동 출력
- 파라미터를 줄이지 않고 **실제 보드 값 그대로** 시뮬레이션

**대본**
> 테스트벤치에는 실제 센서처럼 동작하는 모델을 만들었습니다. trigger가 내려가면 200마이크로초 뒤에 echo를 올리고, 원하는 거리 곱하기 58마이크로초 동안 유지합니다.
> 결과는 파형을 눈으로만 보지 않고, check task로 기대값과 비교해서 PASS, FAIL을 자동으로 출력하게 했습니다. 그리고 시간을 줄인 파라미터가 아니라 보드에 올라가는 값 그대로 돌렸습니다.

## 3. 정상 측정 (1:20 ~ 2:20)

**슬라이드 내용** — 파형 캡처: `start`, `trigger`, `echo`, `debug_state`, `distance`

| TC | 입력 echo | 기대 | 결과 |
|---|---|---|---|
| TC1 | 리셋 직후 | state=IDLE, distance=0, trigger=0 | PASS |
| TC2 | 580us | 10cm, trigger ≥ 10us | PASS (trigger 12.01us) |
| TC3 | 5,800us | 100cm | PASS |
| TC3 | 23,142us | 399cm (센서 최대 4m 근처) | PASS |

**대본**
> 먼저 정상 측정입니다. 리셋 직후에는 IDLE 상태, 거리 0, trigger 0인 것을 확인했습니다.
> 다음으로 10센티미터, 즉 580마이크로초짜리 echo를 넣었습니다. 파형을 보시면 start 펄스가 들어오고, trigger가 12.01마이크로초 동안 올라갑니다. 데이터시트 요구값이 10마이크로초 이상이라 조건을 만족합니다. 이어서 state가 WAIT, DISTANCE, STOP 순서로 바뀌고, echo가 내려가는 순간 distance가 10으로 바뀝니다.
> 같은 방식으로 100센티미터, 그리고 센서 최대 거리에 가까운 399센티미터도 정확히 나왔습니다.

**파형 포인트 (발표 중 커서로 짚을 곳)**
1. start 펄스 → state 0→1, trigger 상승
2. trigger 폭 12us
3. echo 상승 → state 2→3
4. echo 하강 → distance 갱신, state 3→4

## 4. 예외 처리 (2:20 ~ 3:30)

**슬라이드 내용**

| TC | 상황 | 기대 동작 | 결과 |
|---|---|---|---|
| TC4 | 측정 중(DISTANCE) start 재입력 | 무시, 30cm 정상 측정 | PASS |
| TC5 | 측정 끝난 직후(60ms 이내) start | 거부, IDLE 유지 | PASS |
| TC6 | echo가 아예 안 옴 (센서 미연결) | WAIT 36ms 타임아웃 → 0, IDLE 복귀 | PASS |
| TC7 | 물체 없음 (echo 38ms) | DISTANCE 36ms 타임아웃 → 0 | PASS |
| TC8 | echo가 high로 붙어 있음 | start 거부 | PASS |

**대본**
> 다음은 실제 보드에서 생길 수 있는 예외 상황입니다.
> 첫째, 측정 중에 버튼을 또 누르면 어떻게 될까요? start는 IDLE 상태에서만 받기 때문에 무시되고, 30센티미터가 정상으로 측정됐습니다.
> 둘째, 측정이 끝나자마자 다시 누르는 경우입니다. 초음파 잔향 때문에 데이터시트는 60밀리초 이상 간격을 권장합니다. 그래서 60밀리초가 지나기 전 start는 거부되도록 했고, 시뮬레이션에서도 IDLE을 유지했습니다.
> 셋째, 센서가 빠져서 echo가 아예 안 오는 경우입니다. 타임아웃이 없으면 FSM이 WAIT에 영원히 멈춥니다. 36밀리초가 지나면 거리를 0으로 만들고 IDLE로 돌아와서 다음 측정이 가능합니다.
> 넷째, 앞에 물체가 없으면 센서는 echo를 38밀리초 정도 길게 냅니다. 이때도 DISTANCE 상태에서 36밀리초 타임아웃이 걸려 0을 출력합니다.
> 마지막으로 echo가 high로 붙어 있는 비정상 상태에서는 start 자체를 받지 않도록 했습니다.

## 예상 질문 대비

- **왜 58로 나누나요?** 음속 340m/s 기준 1cm 왕복 = 2cm / 0.034cm/us ≈ 58.8us. 정수 카운터로 58을 사용.
- **echo를 왜 2-FF로 받나요?** echo는 클럭과 무관한 외부 신호라 메타안정성 방지.
- **소수점 이하는?** 버림. 예: 579us → 9cm, 580us → 10cm.
- **distance가 9비트인 이유?** 센서 최대 4m(400cm)를 담으려면 9비트(최대 511) 필요. echo가 29.7ms(512cm)를 넘으면 값이 넘쳐 작아지지만, 센서 측정 범위(4m) 밖이라 실사용 범위에서는 문제 없음.
